## 2. Le défaut trouvé : une colonne qui écrit sur le modèle

**Constat.** Le modèle `Employee` range une valeur de colonne soit dans un
champ déclaré, soit dans un dictionnaire de débordement. Le test qui
décidait portait sur `hasattr` :

```python
if hasattr(self, name):
    setattr(self, name, value)
else:
    self.extra[name] = value
```

`hasattr` est vrai pour tout ce que l'objet porte — y compris ses propres
méthodes. Une colonne intitulée **« Value »**, déclarée comme nouveau champ
depuis la page Paramètres, reçoit le nom technique `value` et **écrase la
méthode `value()`** du modèle. L'analyse tombe quelques lignes plus loin sur
`'str' object is not callable`, sans que rien ne désigne la colonne en
cause. Mesuré :

```
  __class__    TypeError: __class__ must be set to a class, not 'str' object
  __dict__     TypeError: __dict__ must be set to a dictionary
  identity     AttributeError: property 'identity' has no setter
  value        ÉCRIT  -> 'injecte'      ← la méthode est remplacée
  assign       ÉCRIT  -> 'injecte'      ← la méthode est remplacée
  issues       TypeError: 'str' object is not callable
```

**Portée.** Ce n'est pas une exécution de code : le modèle n'appelle jamais
ce qu'il reçoit, et une chaîne posée à la place d'une méthode ne fait rien
d'autre que faire échouer l'appel suivant. C'est un défaut de robustesse,
pas une faille. Mais une colonne « Value » n'a rien d'exotique dans un
export anglophone, et un outil ne doit pas tomber dessus.

**Correction.** `assign` n'écrit que dans les champs réellement déclarés par
le modèle, lus une fois pour toutes sur la classe ; tout le reste va dans le
dictionnaire de débordement, où le reste de l'outil sait le lire. Et la page
Paramètres refuse désormais un nom que le modèle emploie déjà, avec une
phrase qui le dit, plutôt que de laisser passer.

**Deux pièges rencontrés en corrigeant**, tous deux pris par la suite de
tests, et qui valent d'être notés parce qu'ils auraient tous deux produit
une correction silencieusement inerte :

1. La liste des champs déclarés, annotée `_NATIFS: frozenset`, devenait
   elle-même un champ de données : chaque salarié en recevait une copie
   vide, et le contrôle ne portait plus sur rien. Elle est désormais une
   `ClassVar`.
2. Le nom saisi par l'utilisateur passait par la fonction qui *évite* les
   collisions. Taper « base_salary » donnait « base_salary_2 », qui n'est
   pas un doublon — et le contrôle de doublon ne voyait plus rien. La
   normalisation et l'évitement de collision sont maintenant deux fonctions
   distinctes.

## 9. Ce que cet audit ne couvre pas

- **La signature Authenticode.** Le binaire n'est pas signé : SmartScreen
  avertira au premier lancement. Un certificat de signature de code est une
  décision de l'entreprise, pas de l'outil.
- **Le poste lui-même.** L'outil lit le fichier qu'on lui donne et écrit où
  on lui dit. Ce que vaut le poste, qui y accède et comment le fichier RH y
  est arrivé ne relèvent pas de l'outil.
- **Le classeur Excel**, qui emporte les données individuelles et, si on le
  lui demande, une copie du fichier source. C'est sa raison d'être — refaire
  chaque calcul — et c'est un choix de conception, documenté dans
  `DOSSIER-RSSI.md` §8.1. Un classeur se transmet : la première feuille le
  dit en toutes lettres.
